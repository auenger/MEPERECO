# MEPER Studio 长对话性能优化计划

## 1. 目标与范围

在保持现有聊天体验、消息完整性和实时执行可见性的前提下，降低长会话的网络、CPU、DOM 及内存开销。覆盖 Desktop（macOS/Windows）与共享 Web 聊天组件；移动端分页作为后续独立阶段，不修改 Windows 同步目录。

本轮不进行全量性能压测；先实施安全、可复用的高收益优化，使用针对性类型检查和逻辑验证。后续根据真实使用情况再调整阈值。

## 2. 已有基础

- 游标分页：以 `created_at + id` 为游标，首屏最近 50 条，向上滚动加载历史。
- React Virtuoso 虚拟滚动：可视区域及上下缓冲区挂载，向上补页保持锚点。
- 富文本：RichContent 使用 memo/useMemo，Mermaid / HTML 通过近视口懒挂载和高度占位。
- Agent 实时事件：WebSocket 更新 Query Cache，live / persisted Assistant 行使用相同 run key。
- 已有数据库索引：chat_message(session_id, created_at)、agent_run_message(run_id, seq)。

保留这些机制，不重新引入虚拟列表库，不更改消息 API 的既有语义或权限边界。

## 3. 分阶段实施

| 优先级 | 优化项 | 实施原则 |
| --- | --- | --- |
| P0-A | 最新消息增量同步 | 实时事件仅协调同步最新窗口，按 message ID 合并/去重；不重新请求全部已加载历史。发生不连续窗口、断线、异常时走权威重同步，保留游标和历史。 |
| P0-B | 历史 Agent 执行过程按需加载 | 已完成消息直接利用持久化正文和已缓存 Run；未缓存的过程用户主动展开后请求，运行中保持实时。保护失败、无回复、附件、复制及流式转持久化行为。 |
| P1-A | 实时事件合批 | 每 Run 约 50ms 合并一次缓存更新，按 seq 去重；正序增量追加，乱序归并；终态及连接清理及时 flush。 |
| P1-B | 稳定列表/Markdown 引用 | 统一两套聊天入口的分页派生；首屏、历史追加和运行中状态变化不重建无关消息行。继续保留已有富文本 memo；不要破坏未闭合 Markdown 围栏及图表挂载。 |
| P2-A | 快速对话休眠 | 关闭后卸载或暂停重型聊天视图及会话查询，保留草稿、会话 ID、轻量状态；工作流嵌入场景单独处理。 |
| P2-B | 长会话内存预算 | 按访问频度、页范围与当前位置管理历史缓存，不直接使用 maxPages 丢弃用户正在浏览的消息；优先回收未活跃 Run 和会话。 |
| P3 | 会话列表、移动端分页及数据库 | 会话列表虚拟化；移动端已有 FlashList 但仍全量取消息，迁移游标分页；真实数据上评估复合索引 `(chat_session_id, created_at, id)`。 |

## 4. 数据正确性约束

- 最新窗口合并不能删除旧页边界处的数据；已缓存的旧消息保留，服务端返回的同 ID 权威记录替换旧版本。
- 会话事件可能重叠、乱序、重放，或与向上加载并行；不能造成重复、跳页或遗漏。检测到不连续窗口回退重同步。
- 断线重连、删除/取消恢复及权限变化维持现有权威校验，绝不为减少请求绕过权限。
- Run 过程折叠不丢弃已持久化的消息正文；展开可读取原有过程。Live → settled 保持同一行 identity，不能重置 Mermaid/HTML 实例。
- 兼容老消息、无回复、失败原因、复制文本和附件；不修改模型上下文、对话历史存储或 Agent 执行流程。
- 不改变 Windows 同步文件夹，也不引入新的依赖。

## 5. 本轮验证（非压力测试）

- 桌面及共享视图 TypeScript 类型检查。
- 增量合并的重叠、去重、断档回退和 Run seq 合并的针对性用例。
- 确保打开历史消息、展开执行步骤、实时输出、失败/停止提示和分页滚动仍可用；实际 Agent 生成与长会话规模测试由后续手动验证。
- 后续使用 1,000 / 10,000 条消息与高频 Run 事件测首屏/滚动、请求量、长任务、内存及掉帧，当前不承诺未经实测的性能数字。

## 6. 本轮实施记录

### 已落地（P0 / P1）

- **P0-A：** `syncLatestChatMessageQueries` 将常规发送、消息事件、Run 完成/失败的分页刷新合并到 80ms 最新窗口同步。客户端记录最近一次服务端确认的消息 ID；只在能证明窗口连续时合并，否则走原有无限分页刷新。已有旧页及游标保持不变；正在进行的历史翻页优先完成，避免覆盖其快照。断线重连和取消恢复保留原有完整同步路径。
- **P0-B：** 冷启动的已完成回复直接渲染持久化正文；通过「查看执行过程」按需获取 Run 详情，失败可重试。已缓存的执行信息和进行中的 Run 仍沿用原有时间线展示；已完成的过程默认折叠。无需后端接口或数据库改造。冷缓存的复制以持久化正文为准，展开详情后沿用现有可见时间线复制规则。
- **P1-A：** 全局 Run 事件按 50ms / run_id 合批，终态先 flush 再处理对应的消息事件；在正序场景跳过全量排序，对乱序/重复 seq 保持原有归并规则并补齐批内去重。
- **P1-B：** 聊天主页与快速对话共享分页派生和乐观追加逻辑；未变化的分页数据不反复 flatten，消息行使用稳定的 message/runId 属性，参与者列表和时间线分段缓存，避免无关的重渲染；折叠详情不构建内部内容。

## 7. 第二轮：桌面/Web 日常资源治理

按已确认的顺序实现快速对话休眠、会话列表虚拟化、非活跃会话/Run 回收。原生移动端暂不纳入。

| 项目 | 实施状态 | 行为 |
| --- | --- | --- |
| 快速对话休眠 | 已实现 | 正常关闭后播放退出动画、保存最后一次草稿变更、释放消息 DOM、富媒体、编辑器与重型 Query observer。发送 HTTP 尚未完成时保持单次提交锁，完成后再卸载；附件沿用独立上传协调器。工作流内嵌对话保留其挂载及完成回填。 |
| 主视图会话列表 | 已实现 | 活跃、归档列表均使用 Virtuoso 固定 56px 行和 session ID key，保留原顺序、置顶、未读、停止与归档操作。 |
| 快速对话会话下拉 | 已实现 | 超过 7 项时使用有界虚拟列表；重命名草稿由父组件持有，不因行回收丢失。 |
| 非活跃会话缓存 | 已实现 | 消息分页及旧消息查询在最后一个 observer 释放后 5 分钟回收；活跃会话无强制分页上限。 |
| 非活跃 Run 缓存 | 已实现 | 最后一个 observer 释放后 3 分钟回收；后台无 observer 的 WS 事件不创建完整/部分 Run 缓存，已有闲置缓存标记过期。保留已打开的只读 Task 执行记录实时订阅。 |

### 7.1 休眠后的唤醒与后台运行恢复（必须保证）

- 关闭快速对话不是取消 Run；Agent 在服务端继续执行，后台 WebSocket 与未读/运行状态提示仍然运行。
- 再打开时恢复会话 ID、输入草稿、窗口大小以及已缓存的消息，立即展示缓存内容。
- **无论缓存是否仍存在，重新挂载的快速对话都校验 pending-run 服务端快照。** 冷缓存直接通过分页 API 加载最近 50 条；暖缓存额外通过最新窗口协调器同步遗漏的新消息，避免正常情况下重取所有历史页。
- 如果 Run 尚在执行：重取完整的 Run 记录，合并获取期间到达的 WebSocket seq，之后继续实时流式展示，不从空记录重新开始，也不因客户端 GC 漏掉后台执行步骤。
- 如果 Run 已结束：通过最新消息窗口展示已持久化的最终回复；执行详情仍遵循前一轮按需展开原则。缓存被回收不等于删除服务端任何数据。
- 活跃消息窗口不强制截断，避免破坏滚动位置。后续才考虑双向游标窗口与更精细的内存预算。

### 7.2 验证

- 第一轮 8 项合并/游标测试；本轮新增 5 项针对性 Run 缓存测试（包括缓存未创建、闲置失效、只读 observer 连续更新、终态失效及睡眠后完整重载继续流式输出）。
- Desktop renderer 类型检查；本地 App 已重新启动，接口正常响应。桌面自动化 native pipe 启动失败，尚未完成实机开关对话、滚动以及后台 Run 唤醒的交互验证；不执行实际 Agent 请求或压测。
- 无后端、数据库、原生移动端或 Windows 同步目录变更。剩余阶段：活跃长会话内存窗口、超长 Markdown 块级增量解析、原生移动端分页，暂不实施。
